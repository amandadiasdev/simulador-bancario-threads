1. Processo e thread

Um processo é um programa em execução, com sua própria memória. Uma thread (fio de execução) é um caminho de execução dentro desse processo. Um processo tem pelo menos uma thread, e pode ter várias.

Pense em uma cozinha (o processo). Os cozinheiros (as threads) compartilham a geladeira, o fogão e a despensa. Mas cada cozinheiro tem as próprias mãos e a própria lista de "onde eu parei" na receita.

Na memória isso significa: as threads compartilham código, dados globais, heap e arquivos abertos. Cada thread tem, só para ela, registradores, contador de programa (PC) e pilha. O PC guarda "qual instrução vem agora". A pilha guarda variáveis locais e chamadas de função.

Por que isso importa: criar uma thread é barato, porque a memória já existe. Criar um processo novo exige copiar ou montar uma memória inteira. Em troca, um erro de uma thread pode derrubar o processo inteiro, porque todas moram na mesma casa.

2. Por que usar threads

Quatro motivos clássicos, com o exemplo de um navegador web:

Capacidade de resposta

  • Uma thread baixa a imagem, outra continua atendendo seus cliques.
  • A interface não congela.

Compartilhamento de recursos

  • As threads já veem a mesma memória.
  • Não precisam de mecanismos extras para trocar dados.

Economia

  • Criar e trocar de thread custa menos que criar e trocar de processo.
  • Menos memória duplicada.

Escalabilidade

  • Com vários núcleos, várias threads rodam ao mesmo tempo de verdade.
  • Um processo de uma só thread usa só um núcleo.

3. Threads de usuário e de kernel

Existem dois "níveis" de thread. Threads de usuário são gerenciadas por uma biblioteca dentro do programa, sem o kernel saber. Threads de kernel são gerenciadas pelo próprio sistema operacional, e só elas podem ser colocadas em um núcleo do processador.

4. Como o escalonador reveza as threads

O escalonador é a parte do kernel que decide qual thread usa cada núcleo agora. Aqui ele usa round-robin: cada thread ganha uma fatia de tempo (o quantum), e depois vai para o fim da fila.

Trocar a thread que está no núcleo é a troca de contexto: o kernel salva os registradores e o PC da thread que sai, e carrega os da que entra. É por isso que cada thread precisa dos seus próprios registradores e PC.

Repare na diferença: com 1 núcleo as threads só se revezam. Isso é concorrência: parecem andar juntas, mas em cada instante só uma executa. Com 2 núcleos duas executam no mesmo instante. Isso é paralelismo.

5. Condição de corrida

Duas threads compartilham a variável contador, que começa em 0. Cada uma quer somar 1. O resultado certo é 2. Mas contador = contador + 1 não é uma instrução só: o processador faz três passos.

LOAD copia o valor da memória para um registrador da thread. ADD soma 1 no registrador. STORE grava o registrador de volta na memória. Entre um passo e outro, o escalonador pode trocar de thread.

Quando o resultado dá 1, aconteceu uma condição de corrida: o resultado depende da ordem em que as threads foram escalonadas. O trecho LOAD, ADD, STORE é uma seção crítica: só uma thread pode passar por ele por vez.

Ative o mutex (exclusão mútua). Ele funciona como uma chave: a thread que faz o LOAD pega a chave, e a outra fica esperando até o STORE devolver. Assim a sequência nunca é interrompida no meio, e o resultado é sempre 2.
